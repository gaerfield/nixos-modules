# Declarative Firefox web apps for Home Manager

This sibling to `gnm.hm.pwaChromium` declares ordinary websites or PWAs via
Home Manager's `programs.firefoxpwa`. Chromium configuration is independent.

## Use

Copy this directory into your Home Manager module tree. Import `default.nix`
and configure `gnm.hm.pwaFirefox`; `example.nix` is a complete starting point
with Gmail, Google Maps and OpenStreetMap. Alternatively import `example.nix`
directly: it imports the module and enables those three apps.

```nix
{
  imports = [ ./pwa-firefox ];
  gnm.hm.pwaFirefox = {
    enable = true;
    apps = [
      {
        id = "gmail";
        title = "Gmail";
        url = "https://mail.google.com/";
        # icon = ./icons/gmail.png;
      }
    ];
  };
}
```

Run your normal Home Manager switch or NixOS rebuild. Launch the generated
Gmail/Maps/OSM desktop entries. There is no `site install`, `runtime install`
or runtime download step. The browser extension and native messaging setup
are unnecessary for this declarative launch workflow.

## Runtime and compatibility

Requires a Home Manager revision with `programs.firefoxpwa.profiles` and null
`manifestUrl` support, and Nixpkgs exposing `firefoxpwa-unwrapped` with its
`firefoxRuntime` override and `wrapFirefox`. Sources checked on 2026-10-05
use FirefoxPWA 2.20.0. Your locked revisions were not supplied; compatibility
with older locks is not established.

The default is `pkgs.firefox-esr-unwrapped`. Nixpkgs copies this runtime into
the FirefoxPWA package, patches it at build time and wraps the result with
Firefox's graphics/media environment. The runtime is immutable and managed
by Nix. This uses the existing package mechanism rather than the experimental
`runtime install --link` path, which is not needed here.

To select regular Firefox instead:

```nix
gnm.hm.pwaFirefox.runtimePackage = pkgs.firefox-unwrapped;
```

An existing manually installed runtime under `$XDG_DATA_HOME/firefoxpwa/runtime`
can take precedence upstream. If you previously installed one, close your PWAs
and move that runtime directory aside before using the module. Do not remove
browser profile directories. Existing `FFPWA_USERDATA`/`FFPWA_SYSDATA` overrides
must also agree with the paths managed here.

## Stable identity and profiles

Set `id` explicitly before first use. Changing `title`, URL, icon or list order
then keeps both IDs and the profile directory stable. The fallback `id` is the
lowercase title with spaces replaced by hyphens; other characters require an
explicit key. IDs/profile keys accept lowercase letters, digits, `_` and `-`.

Each app gets its own profile by default. To share Google login, set
`profile = "google";` on both Gmail and Maps. This shares cookies, storage,
preferences and other profile data, not only the login. Changing the profile
key later selects a different directory; it does not migrate existing data.
Shared profiles also use FirefoxPWA's own process/window behavior.

ULID-shaped IDs encode 128 bits of SHA-256 as Crockford Base32, with separate
site/profile namespaces. The first digit satisfies the ULID overflow rule.
These identifiers are deterministic, not timestamp-based creation records.
Duplicate app keys are rejected.

## Icons, Wayland and persistence

`icon = ./icons/gmail.png;` accepts a Nix path literal; a string such as
`icon = "mail-client";` selects an icon theme name. A remote `iconUrl` (or a
remote URL in `icon`) requires `iconHash`. Do not set both `icon` and `iconUrl`.
Without an icon, menu icon appearance depends on the desktop.

Wayland and XDG portal usage are enabled by default through the verified keys
`config.runtime_enable_wayland` and `config.runtime_use_portals`. Existing
runtime environment variables take precedence. The module assumes your
normal desktop portal services/backends are configured. It does not install
or choose a portal backend. Disable either setting through `enableWayland`
or `usePortals` if needed.

If your module tree declares the `persistence.directories` option used by your
Chromium module, profile directories are registered there by default. On plain
Home Manager no such option is required; profiles use the ordinary persistent
home directory. Set `persistProfiles = false;` to opt out. This does not attempt
to configure other persistence APIs. Only profile directories are registered;
the site registry is regenerated by Home Manager and runtime comes from Nix.
Removed apps' browser data is not deleted automatically.

## Declarative boundary

Home Manager owns `firefoxpwa/config.json` as a read-only Nix-generated file.
CLI or extension operations that attempt to install, remove or update registry
entries can therefore fail. Change the Nix configuration instead. Mutable
browser state still lives in the profile directories and is not reproducible.
A configured manifest URL does not imply that Nix fetches or pins the remote
manifest; Home Manager supplies the initial name/start URL itself.

There is no custom launcher. Home Manager emits
`firefoxpwa site launch <site-id> --protocol %u` and FirefoxPWA handles launch
behavior. The runtime supplies `FFPWA-<site-id>` as its window class/name.
External-link routing, cookie allowlists and Chromium policy flags are not
ported; this module implements the narrower Firefox interface agreed for
Gmail/Maps/OSM. A browser backend does not itself guarantee a particular
performance advantage.

## Validation

- All three Nix files parsed with Nix 2.18.1.
- Evaluated with the actual current Home Manager FirefoxPWA module and
  Nixpkgs module library; package/filesystem dependencies were stubbed.
- Verified isolated and shared profiles, generated registry and desktop
  entries, profile persistence, settings nesting, ESR override wiring,
  duplicate-key rejection, mutually exclusive icon options and operation
  without the custom persistence option.
- Independently verified the Nix ID encoder against Python SHA-256/Base32.

No full package build, user-flake evaluation or graphical Wayland launch was
possible here. Run `nix build .#homeConfigurations.<user>.activationPackage`
(or your usual NixOS build target) before switching, then smoke-test a launch,
login persistence, links, portal dialogs and grouping in your compositor.
